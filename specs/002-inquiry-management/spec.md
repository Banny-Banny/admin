## User Scenarios & Testing *(mandatory)*

### User Story 1 - 문의 목록 조회 및 검색 (Priority: P1)

관리자가 문의하기 페이지에서 고객이 생성한 문의(채팅방) 목록을 조회하고, 검색어나 필터를 사용하여 원하는 문의를 찾을 수 있어야 합니다. 문의 목록은 HTTP 통신을 통해 백엔드 API에서 조회합니다.

**Why this priority**: 문의 목록 조회는 관리자가 고객 문의를 확인하고 관리하는 첫 단계입니다. 이 기능 없이는 관리자가 어떤 문의가 있는지 파악할 수 없습니다.

**Independent Test**: 관리자가 문의하기 페이지에 접속하여 문의 목록을 확인하고, 검색어를 입력하거나 상태 필터를 적용하여 원하는 문의를 찾는 것을 테스트할 수 있습니다. 이 기능만으로도 관리자가 문의를 파악하고 탐색할 수 있는 최소한의 가치를 제공합니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 문의하기 페이지에 접속한 상태, **When** 페이지가 로드되면, **Then** HTTP API (`GET /api/admin/inquiries`)를 통해 고객이 생성한 문의(채팅방) 목록이 조회되고 표시되며 각 문의의 제목, 내용, 고객 정보, 상태, 시간 정보가 표시됩니다.
2. **Given** 관리자가 문의 목록을 확인한 상태, **When** 검색어를 입력하면, **Then** 고객명, 제목, 내용에 검색어가 포함된 문의만 필터링되어 표시됩니다.
3. **Given** 관리자가 문의 목록을 확인한 상태, **When** 상태 필터(PENDING, PROCESSING, COMPLETED 등)를 선택하면, **Then** 해당 상태의 문의만 필터링되어 표시됩니다.
4. **Given** 관리자가 문의 목록을 확인한 상태, **When** 검색어와 필터를 동시에 적용하면, **Then** 두 조건을 모두 만족하는 문의만 표시됩니다.
5. **Given** 관리자가 문의 목록을 확인한 상태, **When** 문의가 한 페이지에 표시할 수 있는 개수보다 많으면, **Then** 페이지네이션(limit, offset)이 표시되고 페이지를 이동할 수 있습니다.
6. **Given** 관리자가 문의 목록을 확인한 상태, **When** 특정 문의방을 삭제하면, **Then** `DELETE /api/admin/inquiries/{id}` API를 호출하여 문의방이 삭제되고 목록에서 제거됩니다.

### User Story 2 - 문의 상세 조회 및 채팅 (Priority: P1)

관리자가 문의 목록에서 고객이 생성한 특정 문의(채팅방)를 선택하여 상세 정보를 확인하고, 채팅 인터페이스를 통해 고객과 소통할 수 있어야 합니다. 채팅 메시지는 Socket.IO WebSocket을 통해 실시간으로 주고받습니다.

**Why this priority**: 문의 상세 조회 및 채팅은 관리자가 고객 문의에 응답하는 핵심 기능입니다. 이 기능 없이는 관리자가 고객과 소통할 수 없습니다.

**Independent Test**: 관리자가 문의 목록에서 특정 문의를 클릭하여 채팅 인터페이스를 열고, 고객과의 대화 내역을 확인하며, 메시지를 입력하여 응답하는 것을 테스트할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 문의 목록을 확인한 상태, **When** 특정 문의를 클릭하면, **Then** 채팅 인터페이스가 열리고 Socket.IO를 통해 `/admin-chat` 네임스페이스에 연결되며 관리자 인증 토큰으로 인증됩니다.
2. **Given** 관리자가 채팅 인터페이스를 열고 Socket.IO 연결이 설정된 상태, **When** 고객이 생성한 문의방의 roomId를 사용하여 `join_room` 이벤트를 전송하면, **Then** 해당 문의방에 입장하고 이전 대화 내역을 HTTP API (`GET /api/admin/inquiries/{id}`)를 통해 조회하여 표시합니다.
3. **Given** 관리자가 채팅 인터페이스를 확인한 상태, **When** 이전 대화 내역이 있으면, **Then** HTTP API를 통해 대화 내역을 조회하고 관리자와 고객의 메시지가 시간순으로 표시되며 발신자 타입(USER/ADMIN)이 구분되어 표시됩니다.
4. **Given** 관리자가 채팅 인터페이스에서 메시지를 입력한 상태, **When** 전송 버튼을 클릭하거나 Enter 키를 누르면, **Then** `send_message` 이벤트를 통해 메시지가 전송되고 대화 내역에 추가되며 고객에게 실시간으로 전달됩니다.
5. **Given** 관리자가 채팅 인터페이스를 확인한 상태, **When** 고객이 새 메시지를 보내면, **Then** `receive_message` 이벤트를 통해 실시간으로 메시지가 수신되고 대화 내역에 추가되어 표시됩니다.
6. **Given** 관리자가 채팅 인터페이스를 확인한 상태, **When** 닫기 버튼을 클릭하면, **Then** `leave_room` 이벤트를 전송하고 Socket.IO 연결이 종료되며 채팅 인터페이스가 닫히고 문의 목록으로 돌아갑니다.
7. **Given** 관리자가 채팅 인터페이스에서 메시지를 입력한 상태, **When** 메시지가 비어있으면, **Then** 전송 버튼이 비활성화됩니다.
8. **Given** 관리자가 채팅 인터페이스를 확인한 상태, **When** 메시지를 읽으면, **Then** `read_alert` 이벤트를 전송하여 읽음 처리가 되고, 고객이 읽었을 때도 `read_alert` 이벤트를 수신하여 읽음 상태를 확인할 수 있습니다.
9. **Given** 관리자가 채팅 인터페이스에서 자신이 보낸 메시지를 확인한 상태, **When** 메시지를 수정하면, **Then** `PUT /api/admin/inquiries/{id}/messages/{messageId}` API를 호출하여 메시지가 수정되고 대화 내역에 반영됩니다.
10. **Given** 관리자가 채팅 인터페이스에서 자신이 보낸 메시지를 확인한 상태, **When** 메시지를 삭제하면, **Then** `DELETE /api/admin/inquiries/{id}/messages/{messageId}` API를 호출하여 메시지가 삭제되고 대화 내역에서 제거됩니다.

### User Story 3 - 문의 상태 관리 (Priority: P2)

관리자가 문의의 상태를 변경하여 문의 처리 진행 상황을 관리할 수 있어야 합니다.

**Why this priority**: 문의 상태 관리는 관리자가 문의 처리 진행 상황을 추적하고 우선순위를 관리하는 데 도움이 됩니다.

**Independent Test**: 관리자가 문의의 상태를 변경하고, 변경된 상태가 문의 목록과 채팅 인터페이스에 반영되는 것을 테스트할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 문의 목록 또는 채팅 인터페이스를 확인한 상태, **When** 문의의 상태를 변경하면, **Then** `PATCH /api/admin/inquiries/{id}/status` API를 호출하여 상태가 변경되고 문의 목록과 채팅 인터페이스에 반영됩니다.
2. **Given** 관리자가 문의를 처리하기 시작한 상태, **When** 상태를 PROCESSING(처리중)으로 변경하면, **Then** 해당 문의가 처리중 상태로 표시됩니다.
3. **Given** 관리자가 문의 처리를 완료한 상태, **When** 상태를 COMPLETED(완료)로 변경하면, **Then** 해당 문의가 완료 상태로 표시됩니다.
4. **Given** 관리자가 문의 목록을 확인한 상태, **When** 상태 필터를 적용하면, **Then** 변경된 상태에 따라 문의 목록이 필터링되어 표시됩니다.

### Edge Cases

- **문의 목록이 비어있을 때**: "문의가 없습니다" 또는 "비어있습니다" 메시지를 표시합니다.
- **검색 결과가 없을 때**: "검색 결과가 없습니다" 메시지를 표시합니다.
- **채팅 인터페이스에서 메시지 전송 중 네트워크 오류가 발생하면**: "네트워크 오류가 발생했습니다" 메시지를 표시하고, 전송 실패한 메시지는 재시도할 수 있도록 처리합니다.
- **동시에 여러 관리자가 같은 문의에 응답하려고 하면**: 이 경우는 발생하지 않을 것으로 예상됩니다.
- **페이지네이션에서 마지막 페이지를 넘어가면**: 이 경우는 발생하지 않아야 하며, 마지막 페이지에서는 다음 페이지 버튼이 비활성화됩니다.
- **문의 상태 변경 중 다른 관리자가 동시에 변경하면**: "처리 중입니다" 메시지를 표시하거나, 먼저 변경한 관리자의 변경사항이 적용됩니다.
- **채팅 메시지가 매우 길 때**: 메시지 입력 시 최대 1500자로 제한하고, 초과 시 입력을 제한합니다.
- **채팅 인터페이스에서 새 메시지가 도착하면**: 실시간으로 메시지가 대화 내역에 추가되고, 필요시 시각적 알림(스크롤, 하이라이트 등)을 제공합니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관리자가 HTTP API (`GET /api/admin/inquiries`)를 통해 고객이 생성한 문의(채팅방) 목록을 조회할 수 있어야 합니다. API는 상태 필터(status), 페이지네이션(limit, offset) 파라미터를 지원해야 합니다.
- **FR-002**: 시스템은 관리자가 문의 목록에서 검색어를 입력하여 문의를 검색할 수 있어야 합니다.
- **FR-003**: 시스템은 관리자가 문의 목록에서 상태 필터를 적용하여 문의를 필터링할 수 있어야 합니다.
- **FR-004**: 시스템은 관리자가 검색어와 필터를 동시에 적용할 수 있어야 합니다.
- **FR-005**: 시스템은 관리자가 페이지네이션을 통해 문의 목록을 탐색할 수 있어야 합니다.
- **FR-006**: 시스템은 관리자가 문의 목록에서 특정 문의를 선택하여 채팅 인터페이스를 열 수 있어야 합니다.
- **FR-007**: 시스템은 관리자가 문의 목록에서 문의방을 삭제할 수 있어야 합니다 (`DELETE /api/admin/inquiries/{id}`).
- **FR-008**: 시스템은 관리자가 채팅 인터페이스에서 문의의 제목, 고객 정보, 초기 문의 메시지를 확인할 수 있어야 합니다.
- **FR-009**: 시스템은 관리자가 채팅 인터페이스에서 HTTP API (`GET /api/admin/inquiries/{id}`)를 통해 이전 대화 내역을 확인할 수 있어야 합니다. API는 페이지네이션(limit, offset) 파라미터를 지원해야 합니다.
- **FR-010**: 시스템은 관리자가 채팅 인터페이스에서 메시지를 입력하고 Socket.IO의 `send_message` 이벤트를 통해 전송할 수 있어야 합니다. 메시지는 roomId와 content를 포함해야 하며, 메시지 길이는 최대 1500자로 제한됩니다.
- **FR-011**: 시스템은 Socket.IO의 `receive_message` 이벤트를 통해 실시간으로 새 메시지를 수신하고 표시할 수 있어야 합니다. 메시지 페이로드는 id, roomId, senderType, senderUserId?, senderAdminId?, content, createdAt을 포함해야 합니다. 새 메시지가 도착하면 대화 내역에 자동으로 추가되고 필요시 스크롤하여 표시합니다.
- **FR-012**: 시스템은 채팅 인터페이스가 열릴 때 Socket.IO를 통해 `/admin-chat` 네임스페이스에 연결하고 관리자 인증 토큰으로 인증해야 합니다. 연결 시 `join_room` 이벤트를 전송하여 고객이 생성한 문의방에 입장하고, 닫힐 때 `leave_room` 이벤트를 전송하여 방을 나가야 합니다.
- **FR-013**: 시스템은 관리자가 고객이 생성한 문의방에 입장할 때 `join_room` 이벤트에 roomId를 필수로 전달해야 합니다.
- **FR-014**: 시스템은 관리자가 메시지를 읽었을 때 `read_alert` 이벤트를 전송하여 읽음 처리를 할 수 있어야 합니다.
- **FR-015**: 시스템은 고객이 메시지를 읽었을 때 `read_alert` 이벤트를 수신하여 읽음 상태를 확인할 수 있어야 합니다.
- **FR-016**: 시스템은 관리자가 채팅 인터페이스에서 Enter 키를 눌러 메시지를 전송할 수 있어야 합니다.
- **FR-017**: 시스템은 관리자가 채팅 인터페이스에서 Shift+Enter를 눌러 줄바꿈을 할 수 있어야 합니다.
- **FR-018**: 시스템은 관리자가 채팅 인터페이스에서 빈 메시지를 전송할 수 없도록 해야 합니다.
- **FR-030**: 시스템은 관리자가 채팅 인터페이스에서 메시지 입력 시 최대 1500자까지만 입력할 수 있도록 제한해야 합니다.
- **FR-031**: 시스템은 채팅 인터페이스에서 새 메시지가 도착하면 실시간으로 대화 내역에 추가하고, 필요시 자동 스크롤하여 최신 메시지를 표시해야 합니다.
- **FR-019**: 시스템은 관리자가 채팅 인터페이스에서 닫기 버튼을 클릭하여 문의 목록으로 돌아갈 수 있어야 합니다.
- **FR-020**: 시스템은 관리자가 문의의 상태를 확인하고 변경할 수 있어야 합니다 (`PATCH /api/admin/inquiries/{id}/status`).
- **FR-021**: 시스템은 문의 목록에서 각 문의의 상태를 시각적으로 구분하여 표시해야 합니다.
- **FR-022**: 시스템은 문의 목록에서 각 문의의 고객 정보(이름, 이메일)를 표시해야 합니다.
- **FR-023**: 시스템은 문의 목록에서 각 문의의 시간 정보를 표시해야 합니다.
- **FR-024**: 시스템은 채팅 인터페이스에서 관리자와 고객의 메시지를 구분하여 표시해야 합니다.
- **FR-025**: 시스템은 채팅 인터페이스에서 각 메시지의 시간 정보를 표시해야 합니다.
- **FR-026**: 시스템은 관리자가 채팅 인터페이스에서 자신이 보낸 메시지를 수정할 수 있어야 합니다 (`PUT /api/admin/inquiries/{id}/messages/{messageId}`).
- **FR-027**: 시스템은 관리자가 채팅 인터페이스에서 자신이 보낸 메시지를 삭제할 수 있어야 합니다 (`DELETE /api/admin/inquiries/{id}/messages/{messageId}`).
- **FR-028**: 시스템은 문의 목록이 비어있을 때 적절한 메시지를 표시해야 합니다.
- **FR-029**: 시스템은 검색 결과가 없을 때 적절한 메시지를 표시해야 합니다.

### Key Entities

- **문의(채팅방)**: 고객이 생성한 문의 사항. 식별자(id), roomId, 고객 정보(이름, 이메일), 제목, 내용, 상태, 생성 시간 정보를 포함합니다. 관리자는 이 문의방에 접속하여 고객과 소통합니다.
- **메시지**: 채팅 인터페이스에서 주고받는 메시지. 식별자(id), roomId, 발신자 타입(senderType: USER | ADMIN), 발신자 식별자(senderUserId 또는 senderAdminId), 내용(content), 전송 시간(createdAt) 정보를 포함합니다. 관리자는 자신이 보낸 메시지를 수정하거나 삭제할 수 있습니다.
- **문의 상태**: 문의의 처리 진행 상황. PENDING(대기중), PROCESSING(처리중), COMPLETED(완료) 등의 값을 가질 수 있으며, 관리자가 `PATCH /api/admin/inquiries/{id}/status` API를 통해 변경할 수 있습니다.
- **Socket.IO 이벤트**: 실시간 통신을 위한 이벤트. join_room(방 입장, roomId 필수), leave_room(방 나가기), send_message(메시지 전송), receive_message(메시지 수신), read_alert(읽음 처리)를 포함합니다.

- **SC-002**: 관리자는 검색어를 입력하여 1초 이내에 필터링된 문의 목록을 확인할 수 있습니다.

- **SC-005**: 관리자는 채팅 인터페이스에서 메시지를 입력하고 WebSocket을 통해 2초 이내에 전송할 수 있습니다.

## Assumptions

- 관리자는 이미 인증 시스템(001-admin-auth)을 통해 로그인한 상태이며, 관리자 액세스 토큰을 보유하고 있습니다.
- 문의(채팅방)는 고객이 생성하며, 관리자는 기존 문의방에 접속하여 조회하고 응답할 수 있습니다.
- 백엔드 API가 다음 엔드포인트를 제공합니다:
  - `GET /api/admin/inquiries`: 문의(채팅방) 리스트 조회
  - `GET /api/admin/inquiries/{id}`: 문의 상세(이력) 조회
  - `DELETE /api/admin/inquiries/{id}`: 문의방 삭제
  - `PATCH /api/admin/inquiries/{id}/status`: 문의 상태 변경
  - `PUT /api/admin/inquiries/{id}/messages/{messageId}`: 문의 메시지 수정
  - `DELETE /api/admin/inquiries/{id}/messages/{messageId}`: 문의 메시지 삭제
- Socket.IO 서버가 `/admin-chat` 네임스페이스를 제공하며, 관리자 인증 토큰을 통해 인증합니다.
- Socket.IO 인증은 auth 객체, Authorization 헤더, 또는 query 파라미터 중 하나의 방식으로 지원됩니다.
- 문의 데이터와 메시지 데이터는 백엔드에서 관리됩니다.
- 관리자는 적절한 권한을 가지고 있습니다.
- 시스템은 반응형 디자인을 지원합니다.
- 브라우저는 최신 버전이며 JavaScript가 활성화되어 있습니다.
- 네트워크 연결이 안정적이며 WebSocket 연결을 지원합니다.
- 관리자는 고객이 생성한 문의방에 입장할 때 roomId를 필수로 제공해야 합니다.
- 메시지는 DB 저장 후 브로드캐스트됩니다.

## Dependencies

- 관리자 인증 시스템 (001-admin-auth): 관리자가 로그인하고 인증 상태를 유지하는 기능
- 백엔드 API: 문의 관련 REST API 엔드포인트 (HTTP 통신)
  - `GET /api/admin/inquiries`: 문의(채팅방) 리스트 조회 API (status 필터, limit, offset 페이지네이션 지원)
  - `GET /api/admin/inquiries/{id}`: 문의 상세(이력) 조회 API (메시지 목록 포함, limit, offset 페이지네이션 지원)
  - `DELETE /api/admin/inquiries/{id}`: 문의방 삭제 API
  - `PATCH /api/admin/inquiries/{id}/status`: 문의 상태 변경 API
  - `PUT /api/admin/inquiries/{id}/messages/{messageId}`: 문의 메시지 수정 API
  - `DELETE /api/admin/inquiries/{id}/messages/{messageId}`: 문의 메시지 삭제 API
- 백엔드 Socket.IO 서버: 실시간 채팅을 위한 Socket.IO 서버
  - `/admin-chat` 네임스페이스 제공
  - 관리자 인증 토큰 기반 인증 (auth 객체, Authorization 헤더, 또는 query 파라미터)
  - Socket.IO 이벤트 지원:
    - `join_room`: 방 입장 (roomId 필수, 고객이 생성한 문의방에 접속)
    - `leave_room`: 방 나가기
    - `send_message`: 메시지 전송 (roomId, content)
    - `receive_message`: 메시지 수신 (id, roomId, senderType, senderUserId?, senderAdminId?, content, createdAt)
    - `read_alert`: 읽음 처리 알림 (roomId, reader: USER | ADMIN)
  - WebSocket 연결 설정 및 관리
  - 실시간 메시지 전송 및 수신
  - 연결 상태 관리
- Socket.IO 클라이언트 라이브러리: Socket.IO 클라이언트 연결 및 이벤트 처리
- UI 컴포넌트 라이브러리: Radix UI 기반 컴포넌트
- 문의하기 페이지: 문의 목록과 채팅 인터페이스를 표시할 페이지
