## User Scenarios & Testing *(mandatory)*

### User Story 1 - 일반 사용자 목록 조회 및 필터링 (Priority: P1)

관리자가 앱을 사용하는 일반 사용자들의 목록을 조회하고, 검색어, 상태, 가입 기간 등의 조건으로 필터링하여 원하는 사용자를 찾을 수 있습니다.

**Why this priority**: 사용자 관리 기능의 핵심이며, 다른 모든 관리 작업(수정, 차단, 탈퇴)의 전제 조건입니다. 목록 조회 없이는 관리자가 사용자를 찾아 관리할 수 없습니다.

**Independent Test**: 관리자 계정으로 로그인한 후 사용자 목록 페이지에 접근하여 목록이 표시되는지, 검색 및 필터 기능이 정상 작동하는지 확인할 수 있습니다. 이 기능만으로도 관리자가 사용자 현황을 파악하는 핵심 가치를 제공합니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 로그인한 상태, **When** 사용자 목록 페이지에 접근, **Then** 일반 사용자 목록이 페이지네이션과 함께 표시됨
2. **Given** 사용자 목록이 표시된 상태, **When** 닉네임 또는 이메일로 검색어 입력, **Then** 해당 검색어와 일치하는 사용자만 필터링되어 표시됨
3. **Given** 사용자 목록이 표시된 상태, **When** 상태 필터(ALL, ACTIVE, INACTIVE) 선택, **Then** 선택한 상태에 해당하는 사용자만 표시됨
4. **Given** 사용자 목록이 표시된 상태, **When** 가입 시작일과 종료일을 설정하여 기간 필터 적용, **Then** 해당 기간 내에 가입한 사용자만 표시됨
5. **Given** 사용자 목록이 표시된 상태, **When** 페이지네이션을 통해 다음 페이지로 이동, **Then** 다음 페이지의 사용자 목록이 표시됨
6. **Given** 검색어와 필터가 적용된 상태, **When** 검색 결과가 없는 경우, **Then** "검색 결과가 없습니다"와 같은 적절한 메시지가 표시됨

### User Story 2 - 사용자 상세 정보 조회 (Priority: P1)

관리자가 목록에서 특정 사용자를 선택하여 해당 사용자의 상세 정보를 조회할 수 있습니다.

**Why this priority**: 사용자 정보 수정, 차단, 탈퇴 등의 작업을 수행하기 전에 사용자의 현재 상태를 확인하는 필수 단계입니다.

**Independent Test**: 사용자 목록에서 특정 사용자를 클릭하거나 상세 보기 버튼을 통해 해당 사용자의 상세 정보가 모달 또는 별도 화면에 표시되는지 확인할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 사용자 목록이 표시된 상태, **When** 특정 사용자 행을 클릭하거나 상세 보기 버튼 클릭, **Then** 해당 사용자의 상세 정보(닉네임, 이메일, 전화번호, 프로필 이미지, 마케팅 동의 여부, 푸시 알림 동의 여부, 가입일, 상태 등)가 표시됨
2. **Given** 사용자 상세 정보가 표시된 상태, **When** 닫기 버튼 클릭, **Then** 상세 정보 화면이 닫히고 목록 화면으로 돌아감

---

### User Story 3 - 사용자 정보 수정 (Priority: P2)

관리자가 일반 사용자의 정보(닉네임, 이메일, 전화번호, 프로필 이미지, 마케팅 동의 여부, 푸시 알림 동의 여부)를 수정할 수 있습니다.

**Why this priority**: 사용자 정보 오류 수정이나 동의 여부 변경 등 일상적인 관리 작업에 필요합니다. 차단/탈퇴보다는 우선순위가 낮지만 중요한 관리 기능입니다.

**Independent Test**: 사용자 상세 정보 화면에서 정보를 수정하고 저장 버튼을 클릭하여 변경사항이 반영되는지 확인할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 사용자 상세 정보가 표시된 상태, **When** 닉네임, 이메일, 전화번호, 프로필 이미지 URL, 마케팅 동의 여부, 푸시 알림 동의 여부 중 하나 이상을 수정하고 저장, **Then** 수정된 정보가 성공적으로 저장되고 목록에 반영됨
2. **Given** 사용자 정보 수정 폼이 열린 상태, **When** 잘못된 형식의 이메일 또는 전화번호를 입력하고 저장 시도, **Then** 유효성 검사 오류 메시지가 표시되고 저장되지 않음
3. **Given** 사용자 정보 수정 중인 상태, **When** 저장 버튼 클릭, **Then** 저장 완료 알림이 표시되고 목록이 자동으로 새로고침됨

---

### User Story 4 - 사용자 차단 및 해제 (Priority: P2)

관리자가 문제가 있는 사용자를 차단하여 서비스 이용을 제한하거나, 차단된 사용자의 차단을 해제할 수 있습니다.

**Why this priority**: 부적절한 행위를 하는 사용자를 즉시 제재하고, 필요시 복구할 수 있는 중요한 관리 기능입니다.

**Independent Test**: 사용자 목록 또는 상세 화면에서 차단 버튼을 클릭하여 사용자를 차단하고, 차단된 사용자에게는 해제 버튼이 표시되어 차단을 해제할 수 있는지 확인할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 활성 상태의 사용자가 목록에 표시된 상태, **When** 해당 사용자의 차단 버튼 클릭하고 확인, **Then** 사용자가 차단 상태로 변경되고 목록에서 상태가 업데이트됨
2. **Given** 차단된 사용자가 목록에 표시된 상태, **When** 해당 사용자의 차단 해제 버튼 클릭하고 확인, **Then** 사용자가 활성 상태로 변경되고 목록에서 상태가 업데이트됨
3. **Given** 사용자 차단 또는 해제 작업 수행 중, **When** 작업 완료, **Then** 성공 알림이 표시되고 목록이 자동으로 새로고침됨
4. **Given** 차단 작업 수행 시, **When** 확인 다이얼로그에서 취소 선택, **Then** 차단 작업이 취소되고 사용자 상태가 변경되지 않음

---

### User Story 5 - 사용자 탈퇴 처리 (Priority: P3)

관리자가 사용자의 탈퇴를 처리할 수 있습니다. 이는 소프트 삭제 방식으로, 사용자 데이터는 완전히 삭제되지 않고 비활성화 상태로 변경됩니다.

**Why this priority**: 사용자 요청에 따른 탈퇴 처리나 정책 위반 시 강제 탈퇴 등에 필요하지만, 차단 기능으로 대부분의 경우를 처리할 수 있어 상대적으로 낮은 우선순위입니다.

**Independent Test**: 사용자 목록 또는 상세 화면에서 탈퇴 처리 버튼을 클릭하고 확인하여 사용자가 탈퇴 상태로 변경되는지 확인할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 활성 또는 차단 상태의 사용자가 목록에 표시된 상태, **When** 해당 사용자의 탈퇴 처리 버튼 클릭하고 확인 다이얼로그에서 확인, **Then** 사용자가 탈퇴 상태(INACTIVE)로 변경되고 목록에서 상태가 업데이트됨
2. **Given** 사용자 탈퇴 처리 작업 수행 시, **When** 확인 다이얼로그에서 취소 선택, **Then** 탈퇴 처리 작업이 취소되고 사용자 상태가 변경되지 않음
3. **Given** 탈퇴 처리된 사용자, **When** 목록에서 상태 필터를 INACTIVE로 설정, **Then** 탈퇴 처리된 사용자가 목록에 표시됨
4. **Given** 사용자 탈퇴 처리 작업 수행 중, **When** 작업 완료, **Then** 성공 알림이 표시되고 목록이 자동으로 새로고침됨

---

### Edge Cases

- 검색어 입력 시 특수문자나 SQL injection과 같은 보안 위협이 포함된 경우 어떻게 처리할까?
- 동시에 여러 관리자가 같은 사용자 정보를 수정하려고 할 때 어떻게 처리할까?
- 네트워크 오류나 서버 오류 발생 시 사용자에게 어떤 피드백을 제공할까?
- 페이지네이션 중 데이터가 변경되어 현재 페이지의 데이터가 없어졌을 때 어떻게 처리할까?
- 차단 또는 탈퇴 처리 중인 사용자가 동시에 다른 작업(정보 수정 등)을 시도할 때 어떻게 처리할까?
- 필터 조건을 적용했을 때 결과가 0건인 경우와 검색 결과가 없는 경우를 어떻게 구분하여 표시할까?
- 사용자 목록 조회 시 매우 많은 데이터(수만 건 이상)가 있을 때 성능은 어떻게 보장할까?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관리자가 일반 사용자 목록을 조회할 수 있어야 합니다
- **FR-002**: 시스템은 사용자 목록에서 닉네임 또는 이메일로 검색할 수 있어야 합니다
- **FR-003**: 시스템은 사용자 목록을 상태(ALL, ACTIVE, INACTIVE)로 필터링할 수 있어야 합니다
- **FR-004**: 시스템은 사용자 목록을 가입 기간(시작일, 종료일)으로 필터링할 수 있어야 합니다
- **FR-005**: 시스템은 사용자 목록을 페이지네이션(limit, offset)으로 나누어 표시해야 합니다
- **FR-006**: 시스템은 관리자가 특정 사용자의 상세 정보를 조회할 수 있어야 합니다
- **FR-007**: 시스템은 관리자가 사용자의 닉네임을 수정할 수 있어야 합니다
- **FR-008**: 시스템은 관리자가 사용자의 이메일을 수정할 수 있어야 합니다
- **FR-009**: 시스템은 관리자가 사용자의 전화번호를 수정할 수 있어야 합니다
- **FR-010**: 시스템은 관리자가 사용자의 프로필 이미지 URL을 수정할 수 있어야 합니다
- **FR-011**: 시스템은 관리자가 사용자의 마케팅 동의 여부를 수정할 수 있어야 합니다
- **FR-012**: 시스템은 관리자가 사용자의 푸시 알림 동의 여부를 수정할 수 있어야 합니다
- **FR-013**: 시스템은 관리자가 사용자를 차단할 수 있어야 합니다
- **FR-014**: 시스템은 관리자가 차단된 사용자의 차단을 해제할 수 있어야 합니다
- **FR-015**: 시스템은 관리자가 사용자를 탈퇴 처리(소프트 삭제)할 수 있어야 합니다
- **FR-016**: 시스템은 사용자 정보 수정 시 입력값의 유효성을 검사해야 합니다
- **FR-017**: 시스템은 사용자 차단, 해제, 탈퇴 처리 시 확인 다이얼로그를 표시해야 합니다
- **FR-018**: 시스템은 모든 사용자 관리 작업 완료 시 적절한 성공/실패 알림을 제공해야 합니다
- **FR-019**: 시스템은 사용자 목록 조회 시 검색 결과가 없을 경우 적절한 메시지를 표시해야 합니다
- **FR-020**: 시스템은 사용자 목록이 로딩 중일 때 로딩 상태를 표시해야 합니다
- **FR-021**: 시스템은 사용자 관리 작업 중 오류 발생 시 사용자에게 오류 메시지를 표시해야 합니다

### Key Entities *(include if feature involves data)*

- **일반 사용자 (User)**: 앱을 사용하는 일반 사용자를 나타냅니다. 주요 속성으로는 고유 ID, 닉네임, 이메일, 전화번호, 프로필 이미지 URL, 마케팅 동의 여부, 푸시 알림 동의 여부, 가입일, 상태(ACTIVE, INACTIVE, BLOCKED) 등이 있습니다. 사용자는 카카오톡 소셜 로그인 또는 자체 로그인을 통해 회원가입할 수 있습니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 사용자 목록을 조회하고 원하는 사용자를 찾는 데 평균 30초 이내로 완료할 수 있어야 합니다
- **SC-002**: 검색어 입력 후 검색 결과가 1초 이내에 표시되어야 합니다
- **SC-003**: 필터 조건 변경 후 필터링된 결과가 1초 이내에 표시되어야 합니다
- **SC-004**: 사용자 정보 수정 작업이 3초 이내에 완료되어야 합니다
- **SC-005**: 사용자 차단/해제 작업이 2초 이내에 완료되어야 합니다
- **SC-006**: 사용자 탈퇴 처리 작업이 2초 이내에 완료되어야 합니다
- **SC-007**: 사용자 목록 페이지는 한 페이지에 최소 20명의 사용자 정보를 표시할 수 있어야 합니다
- **SC-008**: 관리자가 사용자 관리 작업을 수행할 때 95% 이상의 경우 성공적으로 완료되어야 합니다
- **SC-009**: 사용자 목록 조회 시 네트워크 오류나 서버 오류 발생 시 5초 이내에 오류 메시지가 표시되어야 합니다

## Assumptions

- 사용자 목록 조회 API는 검색어, 상태 필터, 날짜 필터, 페이지네이션 파라미터를 지원합니다
- 사용자 정보 수정 API는 닉네임, 이메일, 전화번호, 프로필 이미지 URL, 마케팅 동의 여부, 푸시 알림 동의 여부를 수정할 수 있습니다
- 사용자 차단/해제 API는 사용자 ID를 경로 파라미터로 받아 처리합니다
- 사용자 탈퇴 처리 API는 소프트 삭제 방식으로 사용자 상태를 INACTIVE로 변경합니다
- 모든 사용자 관리 작업은 관리자 권한이 필요하며, 인증된 관리자만 접근할 수 있습니다
- 사용자는 카카오톡 소셜 로그인 또는 자체 로그인을 통해서만 회원가입이 가능합니다
- 사용자 목록은 기본적으로 최신 가입 순으로 정렬됩니다
