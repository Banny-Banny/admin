## User Scenarios & Testing *(mandatory)*

### User Story 1 - 주문 목록 조회 및 필터링 (Priority: P1)

관리자가 주문을 상태/결제상태/기간/유저 기준으로 빠르게 필터링하여, 운영에 필요한 주문을 목록에서 즉시 찾고 처리할 수 있습니다.

**Why this priority**: 주문 운영의 시작점이며, 이후 상세 확인/상태 변경 같은 모든 작업이 목록 탐색에서 출발합니다.

**Independent Test**: 관리자가 다양한 필터 조합을 적용했을 때 목록이 기대한 조건으로 갱신되고, 총 건수/페이지 정보가 함께 제공되어 목록 탐색이 가능합니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 주문 관리 화면에 진입했고, **When** 기본 조건으로 조회하면, **Then** 주문 목록과 총 건수 및 페이지 정보(예: limit, offset)가 함께 표시됩니다
2. **Given** 주문 목록이 표시된 상태에서, **When** 주문 상태/결제 상태/기간/유저 ID 필터를 조합해 조회하면, **Then** 목록은 필터 조건에 맞는 결과로 갱신됩니다
3. **Given** 조회 결과가 0건인 조건에서, **When** 목록을 조회하면, **Then** 빈 상태가 명확히 안내되고 페이지 정보는 일관되게 제공됩니다

---

### User Story 2 - 주문 상세 확인 (Priority: P2)

관리자가 주문의 구성(상품/유저)과 결제 정보를 한 화면에서 확인하여, 문의 대응 및 운영 판단(환불/취소/재처리 등)에 필요한 정보를 빠르게 파악할 수 있습니다.

**Why this priority**: 목록에서 발견한 주문을 실제로 처리하기 위해서는 상세 정보 확인이 필요하며, 특히 “결제 대기”처럼 결제 정보가 없는 케이스를 명확히 구분해야 합니다.

**Independent Test**: 목록의 특정 주문을 선택하면 주문/상품/유저 정보와 결제 정보(있을 경우)가 함께 확인됩니다. 결제 정보가 없는 주문은 “결제 대기”로 구분됩니다.

**Acceptance Scenarios**:

1. **Given** 주문 목록에서 특정 주문을 선택했고, **When** 상세 정보를 조회하면, **Then** 주문/상품/유저 정보가 함께 표시됩니다
2. **Given** 결제 정보가 존재하는 주문을 조회할 때, **When** 상세 정보를 확인하면, **Then** 결제 상태/금액/결제수단/승인 시각을 확인할 수 있습니다
3. **Given** 결제 정보가 없는 주문(예: 결제 대기)을 조회할 때, **When** 상세 정보를 확인하면, **Then** 결제 정보 영역은 “결제 대기 중”으로 표시되어 오해가 없도록 합니다

---

### User Story 3 - 주문 상태 변경 및 결과 확인 (Priority: P3)

관리자가 주문 상태를 변경(예: 대기 → 결제대기/결제완료/취소/실패 등)하고, 변경 결과를 즉시 확인하여 운영 업무를 마무리할 수 있습니다.

**Why this priority**: 운영 처리의 핵심 액션이지만, 상태 변경은 실수 영향이 커서 확인 절차와 결과 피드백이 중요합니다. 목록/상세가 먼저 준비된 이후에 안전하게 제공하는 것이 적절합니다.

**Independent Test**: 관리자가 상태 변경을 요청하면 확인 절차를 거친 뒤, 성공/실패가 명확히 안내되며, 성공 시 목록이 최신 상태로 갱신됩니다.

**Acceptance Scenarios**:

1. **Given** 관리자가 특정 주문의 상태 변경을 시도하고, **When** 확인 절차에서 승인하면, **Then** 주문 상태가 변경되고 변경 성공 메시지가 표시됩니다
2. **Given** 상태 변경이 성공한 후, **When** 목록을 다시 확인하면, **Then** 변경된 주문 상태가 반영된 최신 목록을 볼 수 있습니다
3. **Given** 상태 변경이 실패한 경우, **When** 실패가 발생하면, **Then** 실패 메시지가 표시되고 기존 상태는 유지됩니다

---

### Edge Cases

- 필터 조합이 잘못되었거나(예: 시작일 > 종료일) 의미 없는 조건일 때 사용자에게 어떻게 안내하는가?
- 결제 정보가 없는 주문이 목록/상세에서 “오류”로 보이지 않도록 일관된 표현이 유지되는가?
- 동일 주문을 여러 관리자가 거의 동시에 변경하려고 할 때 결과가 어떻게 안내되는가?
- 주문 ID가 유효하지 않거나 접근 권한이 없을 때(예: 존재하지 않는 주문) 어떻게 안내되는가?
- 목록 조회 중 일시적 장애가 발생했을 때 재시도/복구 흐름이 사용자에게 명확한가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관리자가 주문 목록을 조회할 수 있도록 해야 합니다
- **FR-002**: 시스템은 주문 목록에서 주문 상태 및 결제 상태 기준으로 필터링할 수 있도록 해야 합니다
- **FR-003**: 시스템은 주문 목록에서 유저 ID 및 날짜 범위 기준으로 필터링할 수 있도록 해야 합니다
- **FR-004**: 시스템은 주문 목록에 대해 총 건수와 페이지 탐색에 필요한 정보를 함께 제공해야 합니다
- **FR-005**: 시스템은 주문 목록의 각 항목에 주문/상품/유저 정보와 결제 요약 정보(있을 경우)를 제공해야 합니다
- **FR-006**: 시스템은 결제 정보가 없는 주문을 “결제 대기”로 명확히 구분하여 제공해야 합니다
- **FR-007**: 시스템은 관리자가 특정 주문의 상세 정보를 조회할 수 있도록 해야 합니다
- **FR-008**: 시스템은 주문 상세에서 주문/상품/유저 정보와 결제 정보(있을 경우)를 한 맥락에서 확인할 수 있도록 해야 합니다
- **FR-009**: 시스템은 관리자가 주문 상태를 변경할 수 있도록 해야 합니다
- **FR-010**: 시스템은 주문 상태 변경 시 실수 방지를 위한 확인 절차를 제공해야 합니다
- **FR-011**: 시스템은 주문 상태 변경의 성공/실패 결과를 사용자에게 명확히 안내해야 합니다
- **FR-012**: 시스템은 상태 변경 성공 시 최신 데이터가 반영된 목록을 제공해야 합니다
- **FR-013**: 시스템은 로딩/오류/빈 결과 상태를 사용자에게 이해하기 쉽게 안내해야 합니다

### Key Entities *(include if feature involves data)*

- **주문(Order)**: 주문 식별자, 주문 상태, 총 금액, 생성 시각과 주문에 연결된 상품/유저/결제(선택) 정보
- **상품(Product)**: 상품 식별자, 상품명, 상품 유형
- **결제(Payment)**: 결제 식별자, 결제 상태, 결제 금액, 승인 시각, 결제 수단 (주문에 결제가 없을 수 있음)
- **유저(User)**: 유저 식별자, 닉네임, 이메일, 전화번호
- **조회 조건(Filter)**: 주문 상태, 결제 상태, 유저 ID, 날짜 범위, 페이지 범위(건수/위치)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 기본 조건으로 주문 목록을 조회했을 때, 첫 결과를 확인하기까지 5초 이내에 완료됩니다
- **SC-002**: 관리자가 필터를 변경하여 목록을 갱신했을 때, 결과 확인까지 5초 이내에 완료됩니다
- **SC-003**: 결제 정보가 없는 주문도 운영자가 오해 없이 처리할 수 있도록 “결제 대기”가 일관되게 표시되며, 관련 문의(오표기/누락) 발생률이 5% 미만입니다
- **SC-004**: 관리자가 주문 상세 정보를 확인하고 상태 변경까지 완료하는 데 평균 1분 이내로 마무리할 수 있습니다
- **SC-005**: 오류/빈 결과/로딩 상태에서 사용자가 다음 행동(재시도, 조건 변경, 닫기)을 선택할 수 있도록 안내가 제공되며, 해당 화면 이탈률이 20% 미만입니다
